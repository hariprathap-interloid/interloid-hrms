# Production-Readiness Review — Vite + React Starter Template

**Date:** 2026-07-07 16:20
**Reviewer:** Senior Frontend Architect & DevOps (Claude)
**Stack detected:** Vite 8 · React 19 (React Compiler on) · TypeScript 6 · React Router 7 · Tailwind CSS v4 · shadcn/ui · Zod · Docker (nginx)
**Verdict:** Strong scaffold, **not yet production-ready**. Ships with no data layer, no tests, and no CI/CD.

## 1. Directory & Folder Structure

**Assessment:** Above average. Follows the *bulletproof-react* feature-sliced model — `app/` (wiring), `features/*` (business logic), and shared `components/ hooks/ lib/ services/ config/ types/`. The "features never import each other" rule is documented and enforced by convention. Assets, components, hooks, and utilities *are* properly separated.

**Gaps:**
- **[Medium] No state/context layer.** There is no `app/providers/` composition root and no context/store. `app.tsx` is a bare `<RouterProvider>`. A growing HRMS needs a provider stack (query client, theme, auth, error boundary). → Add `src/app/providers/`.
- **[Medium] `services/` vs `features/*/api.ts` boundary is undefined.** Both exist, both empty. Decide: `services/` = transport (HTTP client, interceptors), `features/*/api.ts` = endpoint functions built on it. Document in `dev.md`.
- **[Low] Empty committed files.** `features/auth/api.ts|hooks.ts|types.ts` are 0 bytes — this contradicts the project's own `.gitkeep` philosophy. Remove until they hold real code.
- **[Low] `skeletons/` as a top-level mirror of `pages/`** is unconventional; colocating a skeleton beside its page/feature scales better as pages multiply. Optional.

## 2. Configuration & Tooling

**TypeScript — excellent (9/10).** `strict`, `noUncheckedIndexedAccess`, `noUnusedLocals/Parameters`, `noImplicitOverride`, `noFallthroughCasesInSwitch`, `verbatimModuleSyntax`, project references. This is stricter than most production apps. Keep as-is.

**ESLint — excellent (9/10).** Type-checked config (`recommendedTypeChecked`) + `react-x` + `react-dom` + hooks + refresh, with a scoped override for shadcn's co-exports. Catches floating promises and unsafe `any`. **[Low]** consider adding `eslint-plugin-jsx-a11y` for an internal tool with forms.

**Prettier — good.** Tailwind plugin present, consistent style.

**Vite config — bare (5/10). This is the weakest config.** Current file only sets plugins + the `@` alias. Missing:
- **[High] No `server.proxy`.** With `VITE_API_URL` pointing at `localhost:3000`, dev requests will hit CORS. A proxy (`/api` → backend) is the standard fix.
- **[Medium] No `build.rollupOptions.output.manualChunks`.** Vendor splitting (react/router/radix) improves long-term caching. Validate first with the existing `npm run analyze`.
- **[Medium] No asset compression.** Add `vite-plugin-compression` (gzip **and** brotli) so precompressed `.br`/`.gz` assets ship — pairs with nginx `gzip_static`/`brotli_static`.
- **[Low] No `build.target`/`sourcemap` policy, no `server.port`/`preview` config, no `define` for build metadata.**

> Suggested `vite.config.ts` additions:
> ```ts
> server: { proxy: { '/api': { target: env.VITE_API_URL, changeOrigin: true } } },
> build: {
>   sourcemap: false,
>   rollupOptions: { output: { manualChunks: {
>     'react-vendor': ['react', 'react-dom', 'react-router-dom'],
>   } } },
> },
> // plugins: add viteCompression({ algorithm: 'brotliCompress' }), viteCompression({ algorithm: 'gzip' })
> ```

## 3. Code Quality & Best Practices

**Good:** React Compiler on (no manual memoization needed), Zod-validated env with a single `@/config/env` source of truth, typed `ImportMetaEnv`, route constants via `paths.ts` with `getHref()`, `cn()` util is idiomatic. `Button` is a clean CVA + Radix `Slot` implementation.

**Issues:**
- **[High] `components.json` points at the wrong CSS file** — `"css": "src/index.css"` but the file is `src/styles/index.css`. `npx shadcn add` will misfire. One-line fix.
- **[High] Dark mode is broken/contradictory.** `.dark {}` + `@custom-variant dark` override the real shadcn tokens but nothing toggles the `.dark` class (no theme provider). Separately, `@media (prefers-color-scheme: dark)` only rewrites **legacy** vars (`--text`, `--bg`, `--accent`…) that aren't exposed via `@theme`, so they affect nothing. Net: dark mode does nothing. → One strategy + a `ThemeProvider`.
- **[Medium] Dead/duplicate token system.** The legacy vars (`--text`, `--bg`, `--accent-bg`, `--social-bg`, `--shadow`, `--code-bg`) look copied from an unrelated template and aren't wired into `@theme inline`. Remove or promote intentionally. (A tool like `knip` would flag this class of dead code.)
- **[Medium] `VITE_API_URL` is validated but never consumed** — there is no data-fetching anywhere (see §4/§services). Dead config today.
- **[Medium] Design system not applied to shipped pages.** `error.tsx`, `not-found.tsx`, `loading.tsx` are raw unstyled `<div>`s and `MainLayout`'s Suspense fallback hardcodes `<div>Loading...</div>` instead of the existing `LoadingPage`. These are the reference examples — they should model tokens/`Button`/skeleton usage.
- **[Low] `body { height: 100vh }`** clips overflow and has the mobile-viewport bug → `min-h-dvh`. `--font-heading` = `--font-sans` is redundant.
- **[Low] Redundant loading paths** — per-route `HydrateFallback` and layout `<Suspense>` overlap; standardize on one.
- **[Low] Env security is otherwise handled well** — only `VITE_`-prefixed vars exposed, `.env` gitignored, `.env.example` committed. No secrets leak. Good.

## 4. Test Suite & Test Cases

**Assessment: 0 / 10 — there is no testing setup of any kind.** No Vitest/Jest, no Testing Library, no jsdom/happy-dom, no Playwright/Cypress, no test files, no config. For something branded a "starter template," this is the single biggest omission — every consumer inherits a codebase with no safety net and no example to copy.

**[High] Establish the baseline:**
- **Unit/component:** Vitest + `@testing-library/react` + `happy-dom` (faster than jsdom). Add `test` and `test:watch` scripts and a `vitest.config.ts` (or merge into `vite.config.ts` via `test:` with `environment: 'happy-dom'`, `globals: true`, a `setupTests.ts`).
- **Critical first tests (the missing edge cases):**
  - `config/env.ts` — Zod schema throws on missing/invalid `VITE_API_URL`, applies defaults. This guards startup.
  - `lib/utils.ts` `cn()` — merge/override/conditional class resolution.
  - `Button` — variant/size class application, `asChild` Slot rendering, disabled state.
  - Router — 404 renders `NotFoundPage`; `ErrorPage` handles both `isRouteErrorResponse` and thrown errors.
- **[Medium] Integration:** once the services layer exists, test a feature slice (auth) with a mocked client (MSW) — request → hook → render.
- **[Medium] E2E:** Playwright smoke test for the app boot + primary route (fits the repo's existing quality bar).
- **[Low] Speed:** `happy-dom` + Vitest threads; keep E2E out of the unit run.

## 5. Build & Deployment Readiness

**Good:** Two-stage Dockerfile (node build → nginx serve), `nginx.conf` has the SPA fallback (`try_files … /index.html`) and 1-year immutable caching on `/assets/`. `.dockerignore` is sensible. Node pinned via `.nvmrc` + `engines`.

**Gaps:**
- **[High] No CI/CD.** No `.github/workflows`. Add a pipeline mirroring the pre-commit gate: `npm ci` → `tsc -b` → `eslint .` → `test` → `build` (+ Docker build/publish on main). Without this, the strict local tooling isn't enforced on PRs.
- **[High] Env is baked at Docker build time only.** `docker-compose.yml` passes `VITE_*` as build args, so one image is locked to one environment; promoting the same artifact across dev/stage/prod is impossible. → For multi-env, template a `/config.js` (or `env.js`) at container start and read runtime config from `window`, keeping the image immutable.
- **[Medium] No compression at build or serve.** Add `vite-plugin-compression` (gzip+brotli) and enable `gzip on;` / `brotli_static` in nginx.
- **[Medium] nginx missing security headers** — no `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy`, or CSP. Cheap to add for an internal HRMS.
- **[Low] `index.html` is not cached-busted-safe by default** — ensure nginx sends `Cache-Control: no-cache` for `index.html` (only hashed `/assets/` should be immutable), else users get stale shells after deploys.
- **[Low] Docker container runs as root; no `HEALTHCHECK`.** Add a non-root user and a healthcheck.
- **[Note] `robots.txt` now says `Allow: /`** while the README claims it blocks all crawlers — reconcile the two (an internal HRMS likely wants `Disallow: /`).

**Platform notes (this specific setup):**
- **Vercel/Netlify:** trivial — framework preset "Vite", build `npm run build`, output `dist`. Add a SPA rewrite (`/* → /index.html`) via `vercel.json` / `netlify.toml`, and set `VITE_*` in the dashboard. Set `Cache-Control: immutable` for `/assets/*`, `no-cache` for `index.html`.
- **AWS S3 + CloudFront:** upload `dist`, configure the SPA fallback as a CloudFront custom error response (403/404 → `/index.html`, 200), immutable cache on hashed assets, short TTL on `index.html`.
- **Docker (current):** production-viable after adding compression + security headers + runtime env injection.

## Bottom line

The **foundation is genuinely good** — the TS/ESLint discipline and folder architecture are better than most production repos. But a starter that ships with **no data layer, no tests, and no CI/CD** is a scaffold, not a production template. Closing the six High-impact items moves this from **6.5 → ~9** and makes it a legitimately production-ready base.
